# Test-design

## 0. Проверка подключения к Qase

- Если проверка соединения с Qase успешная, то преходи к следующему шагу
- Если проверка соединения с Qase провалилась, то эскалируй E2

## 1. Purpose (Назначение)

Скилл test-design создаёт тестовую модель на основании требований, выделенных с помощью Skill_1: Requirement-review.

## 2. Inputs (Входные данные)

Файл `01-requirement-review-v{N}.md` — артефакт, созданный в результате исполнения skill requirement-review.

## 3. Procedure (Процедура)

1. **Режим создания тестовой модели**
   - Указать идентификатор проекта `project_key_tc` в Qase (опционально при публикации в Qase).
   - Запросить значения `Write_mode`:
      - `artifacts_only` (дефолт) — запись запрещена;
      - `create_after_approval` — только после явного approval с ID артефакта;
2. **Загрузка и анализ входных данных**
   - Прочитать `01-requirement-review-v{N}.md`.
   - Проверить `status`:
      - `status=PASS` → перейти на шаг "Декомпозиция требований";
      - `status=FAIL` → прервать работу скилла.
3. **Декомпозиция требований**
   - Сохранить структуру деления на функциональности, направления, функции и принадлежность атомарных требований.
   - Используя техники тест-дизайна, для каждого in-scope требования сгенерировать тестовые сценарии (тест-кейсы). В том числе оптимизировать количество кейсов, используя комбинаторные техники, такие как таблица принятия решений, техника состояний и переходов, попарное тестирование (Pairwise Testing).
4. **Разработка каждого тест-кейса**
   Для каждого сценария сформировать:
   - `id`: `TС-<n>`;
   - `title` — краткий, глагольный, проверяемый;
   - `preconditions` — предусловия для начала сценария: версия приложения, среда, начальное состояние объекта и т. д. (опционально, если заданы в контексте);
   - `steps` — шаги воспроизведения;
   - `expected result` — ожидаемый результат после выполнения всех шагов;
   - `data` — специфические данные для сценария: номер абонента, название услуги, специфическое имя и т. д. (опционально, если заданы в контексте);
   - `requirements` — список требований, покрываемых тест-кейсом;
   - `open_questions` — если при проектировании возникли неясности, например не хватает данных для заполнения (недостающие данные фиксируются как открытые вопросы, не додумываются).
5. **Покрытие требований**
   - Зафиксировать значения:
      - `total_count_req` — общее количество требований из входных данных;
      - `count_covered_reqs_tc` — количество требований, покрытых тест-кейсами;
      - `total_count_tc` — общее количество тест-кейсов;
      - `count_tc_without_reqs` — количество тест-кейсов с пустым списком проверяемых требований;
      - `count_tc_not_covered_req` — количество требований, которые не встречаются ни в одном тест-кейсе (не покрыты);
      - `count_tc_with_open_questions` — количество тест-кейсов, в которых заполнено значение `open_questions`.
   - Проверить покрытие требований тест-кейсами (%):
     ```
     coverage_req_tc = count_covered_reqs_tc / total_count_req * 100%
     ```
6. **Поиск дублей**
   - Для тест-кейсов с одинаковым `requirements` выполнить:
      1) Сравнить 'title' тест-кейсов  на фактическое и смысловое совпадение
      2) Сравнить `preconditions`, `steps` и `expected result` тест-кекйсов  на фактическое и смысловое совпадение
         В случае, если обнаружены совпадения хотя бы по одному пункту, то оставить тест-кейсы, но поместить их номера в список «Дубли» и для каждой пары дублей указать:
      - Номера и заголовки
      - Вердикт: дубликат / вероятный дубликат / пересечение
      - Обоснование: что совпало по смыслу (объект, цель, результат), что различается (контекст).
      - Рекомендация: объединить / связать (link) / оставить раздельно
7. **Расчёт статуса скилла**
   - `count_tc_without_reqs=0` и `count_tc_not_covered_req=0` и `count_tc_with_open_questions=0` и дублей нет → `PASS`.
   - `count_tc_without_reqs>0` или `count_tc_not_covered_req>0` или `count_tc_with_open_questions>0` или есть дубли → `FAIL` → E3.
8. **Отчёт**
   - В директории Artifacts/3.Test-design/ Проверить наличие отчёта вида `03-test-design-v{N}.md`, где N-номер версии предыдущего отчёта
   - Сформировать структурированный отчёт `03-test-design-v{N}.md` по шаблону раздела 5
   - Не перезаписывать предыдущую версию при её наличии, присвоить артефакту название `03-test-design-v{N+1}.md`.
9. **Добавление тест-кейсов в Qase (опционально, по `write_mode`)**
   - `write_mode=artifacts_only` (дефолт) → шаблоны тест-кейсов сохраняются только в артефакте;
   - `write_mode=create_after_approval` → запись только после явного approval; допустить предварительное ознакомление с отчётом (`approve 03-test-design-v{N}.md`) и возможность редактирования/добавления данных; иначе → E3.
   - перед созданием папки (Suite) в проекте в Qase, выполнить поиск существующих Suite и проверку на дубликаты:
      - если в проекте уже существует Suite с таким же или схожим по смыслу названием, то эскалировать к пользователю (E3):
         - продолжить создание без изменений
         - продолжить создание, но изменить название Suite
         - создать тест-кейсы в уже существующем Suite
      - в остальных случаях продолжить создание без изменений

## 4. Rules (Правила)

- Каждый тест-кейс должен покрывать одно требование.
- Не должно быть тест-кейсов, не связанных ни с одним требованием.
- Каждое требование должно быть покрыто минимум одним тест-кейсом.
- Не добавлять новые требования.
- Не изменять существующие требования.
- Не додумывать требования при нехватке данных — фиксировать их как `open_questions`.
- Не выдавать предположения за подтверждённые данные.
- При любом значении `write_mode` артефакт сохраняется всегда, независимо от результата публикации.
- **Идемпотентность:** при повторном запуске скилла, в случае отсутствия изменения во входных данных, результат анализа совпадает с предыдущим запуском.
- Повторный запуск создаёт новую версию артефакта, предыдущая сохраняется.
- **Конфиденциальность:** данные требований не покидают разрешённые инструменты.
- При наличии нескольких артефактов одного события, но с разной датой создания и/или версией, использовать только с самой поздней датой создания и/или версией

## 6. Completion Area (Критерии завершения)

Скилл считается успешно завершённым, когда все условия выполнены:

- Входные данные прочитаны.
- Полнота декомпозиции соблюдена:
   - `covered_reqs_tc = 100%` — каждое требование из QG-1 покрыто минимум одним тест-кейсом;
   - `total_count_tc > 0`.
- Для каждого тест-кейса заполнены: `id`, `title`, `preconditions`, `data`, `steps`, `expected result`, `requirements`.
- Отсутствуют дубликаты.
- `Status` скилла вычислен.
- Присутствует заключение о работе скилла.
- Отсутствующая информация и необходимые вмешательства зафиксированы (при наличии).
- Сформирован структурированный отчёт в виде артефакта `03-test-design-v{N}.md` (с версией `-vN`, без перезаписи предыдущей).
- Сформированные Tests (в зависимости от значения `write_mode`) либо только сохранены в артефакте, либо в дополнение опубликованы в Qase.
