# Requirement-review

## 1. Purpose (Назначение)

Выполнить системный анализ требований для дальнейшей работы агента. Сформировать структурированный отчёт по итогу анализа для ознакомления пользователем.

## 2. Inputs (Входные данные)

Файл с документацией или ссылки на Confluence, содержащий:

- текст требований;
- связанные с требованиями бизнес-правила;
- критерии приёмки.

> Skill не должен самостоятельно искать недостающую информацию за пределами входных данных.

## 3. Procedure (Процедура)

1. Читать документацию из п. 2 с требованиями из документа или из Confluence.
2. Определить общую функциональность.
3. Выделить отдельные направления и функции (если есть).
4. Выделить требования.
5. Разбить требования на атомарные единицы `REQ-*`.
6. Разбить полученные атомарные единицы `REQ-*` на группы «функциональные» и «нефункциональные».
7. Разбить полученные атомарные функциональные единицы `REQ-*` по направлениям.
8. Выделить бизнес-правила.
9. Выделить ограничения. При отсутствии указать в группе «Выявленные дефекты документации».
10. Определить наличие критериев приёмки. При наличии выделить в отдельную группу «Критерии приёмки». При отсутствии указать в группе «Выявленные дефекты документации».
11. Проверить требования на наличие противоречий. При обнаружении указать в группе «Выявленные дефекты документации».
12. Проверить требования на наличие неоднозначностей. При обнаружении указать в группе «Выявленные дефекты документации».
13. Проверить требования на наличие неполноты. При обнаружении указать в группе «Выявленные дефекты документации».
14. Проверить наличие пользовательских сценариев (Use Cases). При обнаружении выделить содержимое раздела в группу «Пользовательские сценарии».
15. Проверить пользовательские сценарии на соответствие требованиям. При обнаружении расхождений или дополнительных условий и правил добавить соответствующую запись в блок «Пользовательские сценарии».
16. Зафиксировать значения:
    - `analyzed_count_req` - ;
    - `total_count_req` - ;
    - `blocker_count_req` - ;
      17.Расчёт статуса задачи (`status`):
    - `blocker_count_req=0`, `analyzed_count_req=total_count_req` → `status=PASS`;
    - `blocker_count_req=0`, `analyzed_count_req<total_count_req` → `status=FAIL` → E1;
    - `blocker_count_req>0` → `status=FAIL` → E1;
    - невозможность вычислить критерии → E2.
17. В директории Artifacts/1.Requirement-review/ Проверить наличие отчёта вида `01-requirement-review-v{N}.md`
18. Сформировать структурированный отчёт `01-requirement-review-v{N+1}.md`, где N-номер версии предыдущего отчёта с перечислением пунктов при их наличии:
    - дата запуска текущей проверки по шаблону YYYY-MM-DD HH:mm:ss
    - сообщение о недоступности документации;
    - название проекта
    - направление, общая функциональность проекта
    - тип проекта (web, мобильное приложение, пк приложение)
    - проектируемые функции и относящиеся к ним функциональные требования
    - нефункциональные требования;
    - пользовательские сценарии;
    - выявленные дефекты документации;
    - статус (обязательно).

## 4. Rules (Правила)

При выполнении анализа необходимо соблюдать правила:

- При ошибке чтения или отсутствии доступа к файлу или ссылке с документацией повторить попытку 3 раза. При повторении ошибки остановить работу скилла и выдать сообщение. Сформировать `01-requirement-review-v{N}.md` с сообщением об ошибке, например: «отсутствуют входные данные», «ошибка при открытии inputs», «ошибка при переходе по ссылке из inputs» и т. д.
- Не изменять текст требований и бизнес-правил.
- Не добавлять новые требования и бизнес-правила.
- Не додумывать требования при нехватке данных — фиксировать нехватку как проблему.
- Не выдавать предположения за подтверждённые данные.
- При невозможности выделить отдельные пользовательские сценарии (Use Cases) и сформировать их в структурированный список — скопировать содержимое соответствующего раздела без изменений.
- Не вносить изменения в исходную документацию.
- Не проектировать в рамках этого скилла задачи Jira.
- Не проектировать в рамках этого скилла тест-кейсы в Qase.
- Не выполнять действия, не относящиеся к анализу.
- **Идемпотентность:** при повторном запуске скилла, в случае отсутствия изменения во входных данных, результат анализа совпадает с предыдущим запуском.
- Повторный запуск создаёт новую версию артефакта, предыдущая сохраняется.

## 6. Completion Area (Критерии завершения)

Скилл считается успешно завершённым, когда все условия выполнены:

- Входные данные проанализированы.
- Требования и бизнес-правила зафиксированы.
- Ограничения и критерии приёмки зафиксированы, либо указано, что они не обнаружены.
- Противоречия, неоднозначности и неполнота выявлены, либо указано, что они не обнаружены.
- Отсутствующая информация зафиксирована.
- Сформирован структурированный результат анализа в виде артефакта `01-requirement-review-vN`.
