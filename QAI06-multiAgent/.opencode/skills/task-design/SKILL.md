# Task-design

## 0. Проверка подключения к Jira

- Если проверка соединения с Jira успешная, то преходи к следующему шагу
- Если проверка соединения с Jira провалилась, то эскалируй E2

## 1. Purpose (Назначение)

Скилл task-design проектирует задачи Jira на основе анализа требований:

- либо формирует задачи на проектирование и тестирование функционала при успешном прохождении Quality Gate QG-1;
- либо формирует задачи на исправление обнаруженных дефектов документации.

## 2. Inputs (Входные данные)

Файл `01-requirement-review-v{N}.md` — артефакт, созданный в результате исполнения skill requirement-review.

## 3. Procedure (Процедура)

1. **Режим создания задачи**
    - Агент запрашивает идентификатор проекта `project_key` в Jira (опционально при публикации в Jira).
    - Запросить значения `Write_mode`:
        - `artifacts_only` (дефолт) — запись запрещена;
        - `create_after_approval` — только после явного approval с ID артефакта;
2. **Загрузка и анализ входных данных**
    - Прочитать `01-requirement-review-v{N}.md`.
    - Проверить `status`:
        - `status=PASS` → перейти на шаг "Декомпозиция требований";
        - `status=FAIL` → перейти на шаг "Анализ дефектов документации и типов эскалации".
3. **Декомпозиция требований**
    - Разложить in-scope требования на задачи по функциональностям, направлениям и функциям.
    - Зафиксировать количество требований, покрытых задачами, — `count_covered_reqs`.
    - Зафиксировать общее количество требований `total_count_req` из входного артефакта.
    - Перейти на Шаг 5.
4. **Анализ дефектов документации и типов эскалации**
    - Зафиксировать каждый тип эскалации из входного артефакта.
    - Для дефектов документации зафиксировать принадлежность к типу эскалации.
    - Перейти на Шаг 5.
5. **Разработка каждой задачи**
   Для каждой задачи сформировать:
    - `id`: 'project_key-{n}', если project_key не указан, то `TASK-{n}`;
    - `title` — краткий, глагольный, проверяемый;
    - `description` — что и зачем, границы, контекст;
    - `component`, `labels` — опционально, если заданы в контексте;
    - `requirements` — список требований, покрываемых задачей;
    - `open_questions` — если при проектировании возникли неясности, например не хватает данных для заполнения (фиксируются, не додумываются).
6. **Покрытие требований**
    - Зафиксировать значения:
        - `total_count_req` — общее количество требований из входных данных;
        - `count_covered_reqs` — количество требований, покрытых задачами;
        - `total_tasks_count` — общее количество задач;
        - `count_tasks_without_reqs` — количество задач с пустым списком проверяемых требований;
        - `count_not_covered_req` — количество требований, которые не встречаются ни в одной задаче (не покрыты);
        - `count_tasks_with_open_questions` — количество задач, в которых заполнено значение `open_questions`.
    - Проверить покрытие требований задачами (%):
      ```
      coverage_req_task = count_covered_reqs / total_count_req * 100%
      ```
7. **Поиск дублей**
    - Для задач с одинаковым `requirements` выполнить:
        1) Сравнить 'title' задач  на фактическое и смысловое совпадение
        2) Сравнить 'description' задач  на фактическое и смысловое совпадение
           В случае, если обнаружены совпадения хотя бы по одному пункту, то оставить задачи в отчёте, но не публиковать в Jira
        3) Поместить номера повторяющихся задач в список «Дубли» и для каждой пары дублей указать:
          - Номера и заголовки
          - Вердикт: дубликат / вероятный дубликат / пересечение
          - Обоснование: что совпало по смыслу (объект, цель, результат), что различается (контекст).
          - Рекомендация: объединить / связать (link) / оставить раздельно
8. **Расчёт статуса скилла**
    - `count_tasks_without_reqs=0` и `count_not_covered_req=0` и `count_tasks_with_open_questions=0` и дублей нет → `Status=PASS`.
    - `count_tasks_without_reqs>0` или `count_not_covered_req>0` или `count_tasks_with_open_questions>0` или есть дубли → `Status=FAIL` → эскалация E3.
9. **Отчёт**
    - В директории Artifacts/2.Task-design/ Проверить наличие отчёта вида `02-task-design-v{N}.md`, где N-номер версии предыдущего отчёта
    - Сформировать структурированный отчёт `02-task-design-v{N}.md` по шаблону раздела 5
    - Не перезаписывать предыдущую версию при её наличии, присвоить артефакту название `02-task-design-v{N+1}.md`.
10. **Добавление задач в Jira (опционально, по `write_mode`)**
    - `write_mode=artifacts_only` (дефолт) → шаблоны задач сохраняются только в артефакте;
    - `write_mode=create_after_approval` → запись только после явного approval; допустить предварительное ознакомление с отчётом (`approve 02-task-design-v{N}.md`) и возможность редактирования/добавления данных; иначе → E3.

## 4. Rules (Правила)

- Каждая задача, реализуемая в рамках одного спринта, — одна проверяемая цель.
- Каждая задача должна покрывать минимум одно требование.
- Каждое требование должно быть покрыто задачей.
- Одна задача может порождать несколько подзадач.
- Каждая задача обязана ссылаться на `REQ-*`; нессылающиеся задачи недопустимы.
- Не добавлять новые требования и бизнес-правила.
- Не додумывать требования при нехватке данных — фиксировать их как проблемы.
- Не выдавать предположения за подтверждённые данные.
- При любом значении `write_mode` артефакт сохраняется всегда, независимо от результата записи.
- **Идемпотентность:** при повторном запуске скилла, в случае отсутствия изменения во входных данных, результат анализа совпадает с предыдущим запуском.
- Повторный запуск создаёт новую версию артефакта, предыдущая сохраняется.
- **Конфиденциальность:** данные требований не покидают разрешённые инструменты.

## 6. Completion Area (Критерии завершения)

Скилл считается успешно завершённым, когда все условия выполнены:

- Входные данные прочитаны.
- Полнота декомпозиции соблюдена:
    - `covered_reqs = 100%` — каждое требование из QG-1 покрыто ≥ 1 задачей;
    - `total_tasks_count > 0`.
- Для каждой задачи заполнены: `id`, `title`, `description`, `requirements`.
- Отсутствуют дубликаты.
- `Status` скилла вычислен.
- Присутствует заключение о работе скилла.
- Отсутствующая информация и необходимые вмешательства зафиксированы (при наличии).
- Сформирован структурированный отчёт в виде артефакта `02-task-design-v{N}.md` (с версией `-vN`, без перезаписи предыдущей).
- Сформированные Tasks (в зависимости от значения `write_mode`) либо только сохранены в артефакте, либо в дополнение опубликованы в Jira.
