## 1. Проект

| Параметр | Значение |
|---|---|
| Название проекта | Лендинг «Мини-маркет» (MVP) |
| Основное направление проекта | E-commerce / лендинг для проверки спроса и сбора заявок (витрина + корзина + заявка) |
| Тип проекта | **Web** (адаптивное веб-приложение, mobile-first лендинг) |
| Код проекта | В требованиях **не указан**. В Jira доступен проект с задачами по этой странице (AITST). Код не выдуман, зафиксирован как отсутствующий (см. DEF-19). |
| Владелец продукта | Product Owner |
| Бизнес-заказчик | Маркетинг / E-commerce |

**Контекст (из §2, дословно по смыслу):** компании нужен быстрый и недорогой MVP-лендинг для проверки спроса на товары и сбора первых заказов. Минимальный путь пользователя: **зашёл → авторизовался → выбрал товары → добавил в корзину → оформил заявку**.

**Бизнес-цели и метрики (§3):**

| ID | Цель | Метрика успеха (KPI) |
|---|---|---|
| BG-1 | Проверить спрос на товары через лендинг | ≥ 100 оформленных заявок в первый месяц |
| BG-2 | Снизить барьер входа для покупателя | Конверсия «визит → авторизация» ≥ 25% |
| BG-3 | Обеспечить понятный путь покупки | Конверсия «корзина → заявка» ≥ 40% |
| BG-4 | Собрать контактные данные для повторных продаж | ≥ 80% заявок с валидным телефоном/email |

### 2.1 Функциональные требования

#### Направление: Авторизация (§6.1)

| ID | Требование (источник) |
|---|---|

## 4. Пользовательские сценарии (Use Cases)

**Отдельный раздел «Пользовательские сценарии» в документе отсутствует** (дефект DEF-15). Структурированный список UC из документа сформировать невозможно.

Содержимое раздела §10 «Критерии приёмки MVP (бизнес-уровень)» приведено без изменений:

> MVP считается успешным, если:
> - Пользователь может пройти путь: каталог → авторизация → корзина → заявка без ошибок.
> - Все ключевые события логируются и доступны для анализа.
> - Лендинг корректен на мобильных и десктопе.
> - Заявки доходят до менеджера с валидными контактными данными.

Единственный сквозной сценарий, выводимый из §10 и §2 (помечен как **производный, не документированный** — используется только как ориентир, не как требование):

- **UC-main (производный):** Пользователь заходит на лендинг → просматривает каталог → авторизуется → добавляет товары в корзину → оформляет заявку → получает подтверждение.

### 4.1 Проверка пользовательских сценариев на соответствие требованиям

В связи с отсутствием раздела Use Cases (DEF-15) полноценная проверка сценариев на соответствие требованиям **невозможна**. Производный UC-main не противоречит требованиям REQ-1 – REQ-19, но не покрывает:
- прерывание авторизации / возврат к прерванному действию (REQ-5);
- пустую корзину (REQ-15);
- недоступный товар (REQ-8);
- восстановление пароля (отсутствует в требованиях — DEF-09).
