## 3. Принципы проектирования задач

1. **Два блока:** **A** — доработка требований (дефекты документа), **B** — проектирование/тестирование функционала (тестовая модель).
2. Один блок A-задачи = один **проверяемый результат в документе**; группировка по логическим пакетам, а не по принципу «один дефект — одна задача».
3. Каждая задача **обязана** ссылаться на `REQ-*` (skill §4). Задачи без `requirements` отсутствуют.
4. Границы требований (`REQ-*`) **не изменяются**: формулировки взяты из v7 §3.1–§3.2, границы направлений — по §3.3 (маппинг после вставки FR-AUTH-7, сдвиг +1 начиная с каталога).
5. Недостающие данные → `open_questions`, не додумываются.
6. `component`: `Documentation` для Блока A; `Auth` / `Catalog` / `Cart` / `Order` / `NFR` для Блока B.
7. `priority` Блока A = максимальная серьёзность покрываемого дефекта; Блока B = по критичности направления с учётом waiver.
